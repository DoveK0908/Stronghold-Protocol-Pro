Part of [DESIGN.md](../DESIGN.md)。0.3.3 于 2026-10-25 作为 0.3.2 的热修复发布（released 2026-10-25），仅包含 round53 的商店装备空栏、满整备区互换与跨版本图标缓存三项修复。

## 36. 0.3.3

### 36.1 第一期商店装备核查与空栏显示（round53 shopequip，2026-10-25）

维护者在 0.3.2 的第一期游玩中报告「商店里面不卖装备」。官方第一期的商店表只在调度中心 5–6 级开放装备栏
（下表），低等级时没有装备是官方行为；本次以对应时期的官方表确定开放等级，没有将第二期的开放等级移植给第一期。
（更正：本节原写维护者「确认官方第一期会出售装备」，与报告原话不符。）

#### 复现结论与修正范围

对 `act1autochess`、`act1autochess@V1_1`、`act2autochess@V2_1` 的全部大厅模式（单人／四人 ×
标准 FUNNY／险境 NORMAL／绝境 HARD）各从 1 升至 6 级，升级后主动刷新，每名玩家购买装备。
在改动前即得到下表结果：第一期两个版本都在 5–6 级正常出售，第二期上半在 1–6 级正常出售。
本次没有复现「满足等级并刷新后仍永远没有装备」，不能把它宣称为已找到根因的服务端缺货问题。

确认的客户端问题：`shopBar.js` 按现存卡片的 `kind` 划分两栏，把所有 `null` 都当干员空位；第一期
4→5 级新增的装备位恰好是 `null`，因此跑到干员栏，装备区则错误显示 `SOLD OUT / 已购买`。
1–4 级根本没有装备位时也显示「已购买」。修正为服务端 `m.private.shop.layout` 发送实际干员／装备
位数，客户端据此定位空栏；装备位打开而未刷新时使用现有「空栏位：刷新或下回合开始时补满」提示，
未开放时不画售罄卡。已购买的真实装备仍显示「已购买」。抽取、库存、价格、升级后不自动补货的规则不变。
旧存档／mock 没有 layout 时仍按卡片种类推断（兼容处理；[ASSUMED]，无法恢复旧帧中 `null` 的原始种类）。

### 36.2 满休整区互换回归（round53 benchswap，2026-10-25）

维护者在第一期的 0.3.2 游玩中报告「休整区满的时候没法把休整区的干员跟场上的互换了」。

`server/match/player/placement.js` 在手牌／临时区→场上占位、场上→手牌干员这两个分支中，
先检查 `config.version.rules.benchFullSwap === false && freeSlot(hand) < 0`，于是尚未腾出来源位置
就返回 `HAND_FULL`。第一期两个 profile 均写入 `benchFullSwap: false`，第二期两个版本没有此限制。
客户端 `canPlace` 已按交换后的占位数判断，并没有相同的第一期限制；故可拖入并确认朝向，却被服务端拒绝。

### 36.3 跨版本装备贴图与渲染查表缓存（round53 iconcache，2026-10-25）

#### 复现与根因

维护者报告：第一期下半玩过一局后切到默认第二期下半，商店的「见钱眼开玩偶」图标正常，购买后整备区却
显示「迅捷作战粮」。用真实版本 host、Chrome 和 Pixi 渲染器在同一页面内复现；反向切换也复现。
购入后的 `ItemView.info.icon`、商店和详情的图片地址已经正确，但整备区贴图的 canvas 像素仍是上一版。
回归在修正前双向均失败，因此不能只用「URL 已更新」作为验收。

来源：`data/items.json` 与 `data/versions/act1autochess/items.json`（§36.1 所列官方表的构建产物）。
两个版本的 `chess_item_2_07_e_a` 分别指向 `trap_1116_acarm116`（见钱眼开玩偶）和
`trap_1051_acarm051`（迅捷作战粮），同为 2 阶；`chess_item_2_01_e_a` 也分别是「不屈弹射器」和
「歌利亚头盔」。装备 ID 是版本内的记录键，不能当跨版本图片身份。

根因在 `public/js/render/units.js` 的 `ItemView`：把 `defId` 交给 `render/textures.js` 的
`itemTexture`。后者的模块级 `_items` 缓存贯穿页面生命周期，键为「调用者的 key、是否有图、边框色」；
